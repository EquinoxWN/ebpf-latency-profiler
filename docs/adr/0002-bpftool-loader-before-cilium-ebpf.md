# ADR 0002: Load probes with bpftool in M1, move to a cilium/ebpf loader in M2

- **Status:** Accepted

## Context

The M1 deliverable is the kernel side: eBPF programs on tracepoints and kprobes that build latency
histograms inside BPF maps. Something must still compile, load and attach them to prove they work.
The roadmap gives the Go loader (cilium/ebpf, CO-RE, Prometheus) its own milestone, M2. The author's
machine runs Windows, so every kernel run happens in CI.

Options:

1. **bpftool** (`prog loadall obj.o DIR pinmaps DIR autoattach`, then `map dump -j`).
2. **cilium/ebpf** from Go now, with `bpf2go`-generated bindings.
3. **libbpf C loader** (skeleton generated by `bpftool gen skeleton`).

## Decision

Use bpftool in M1. The Go side reads bpftool's JSON map dumps (`internal/bpfdump`) and checks the
tracepoint layouts (`check-format`). The cilium/ebpf loader is built in M2, where CO-RE and the
Prometheus exporter belong.

## Consequences

- **Gained:** the Go module has no third-party dependencies in M1 (govulncheck scans only the
  standard library); the kernel programs are proven independently of any loader; M2 has a clear,
  separate scope.
- **Lost:** M1 needs `bpftool` on the host and root to pin objects in `/sys/fs/bpf`; the user runs
  two commands (load and dump) instead of one binary; programs stay attached until the pin
  directory is removed (the CI script removes it on exit).
- **Risk:** `autoattach` needs a recent bpftool (v7.x, shipped with Ubuntu 24.04 kernels). An older
  bpftool fails the CI job with a clear error rather than silently.
- Option 3 was rejected because a C loader would be replaced by the Go loader in M2 anyway.
