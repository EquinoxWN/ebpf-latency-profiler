## CI-only kernel run (what the `probes` job does)

1. Installs `clang`, `llvm`, `libbpf-dev` and the runner kernel's `linux-tools` (bpftool).
2. `make bpf build`: `clang -O2 -g -Wall -Werror -target bpf` (the `_Static_assert`s fail the build if
   a mirrored struct is laid out differently) and the Go CLI.
3. `sudo ebpf-latency-profiler check-format`: the 5 tracepoint layouts against the runner kernel.
4. `sudo scripts/probe-run.sh`: `bpftool prog loadall … autoattach`, 3 s of 2×nproc busy loops,
   16 MiB of direct-I/O writes and reads, 200 `O_DSYNC` writes, then `bpftool -j map dump` of each
   histogram, `render`, and `-min-count 1` per probe. Each probe's event count and p50/p99 bucket
   bounds are printed as a `::notice` (or `::error` if no events were counted).

No kernel numbers are quoted here because none were measured on the author's machine; read them from
the CI run's annotations.

## DMAIC summary

- **Define:** RFC 0001 (problem, users, CTQs).
- **Measure:** this file; local Go results above, kernel results from CI annotations.
- **Analyze:** the main defect risk is a silent tracepoint layout mismatch (wrong offsets read
  garbage pids or sectors without any error). Root cause: classic tracepoints are read by offset.
- **Improve:** layouts are pinned three ways: `_Static_assert` in C, a Go test that ties the C
  asserts to the catalog, and `check-format` against the running kernel before loading.
- **Control:** CI runs lint, tests and govulncheck on every push, and the `probes` job fails if the
  layout check fails or any histogram stays empty.
